# 07. 캐시 예제와 성능 ★ (0.5시간)

**한 줄 답**: 느린 원본(50ms) 앞에 미니 Redis를 캐시로 둡니다(cache-aside). 데워진 캐시는 처리량 약 19배, 중앙값 응답 55ms → 2.8ms였습니다.

> 흐름: 클라이언트 → 캐시 API → **[미니 Redis 조회 → 없으면 원본 → 캐시에 저장]**

## 꼭 알 것: 캐시 API 규칙 5개 ([CacheApiMain.java](../src/main/java/example/cacheapi/CacheApiMain.java))

| 규칙 | 안 하면 생기는 일 | 위치 |
|---|---|---|
| 쓰기는 **원본 갱신 → 캐시 삭제** 순서 | 반대 순서면 사이에 들어온 읽기가 옛 값을 다시 캐시에 넣는다 | :151 |
| single-flight | 인기 키가 만료되는 순간 같은 키 요청이 모두 원본으로 몰린다 | :118, :125 |
| TTL ±10% | 같은 시각에 저장된 키들이 한꺼번에 만료된다 | :139 |
| 없는 키도 30초 캐시 | 없는 키를 반복 조회하면 원본을 계속 두드린다 | :135 |
| TTL과 함께 저장 | 무효화를 놓친 값이 영원히 남는다 | |

A~E는 `run.sh`의 `-D` 설정 없이 측정했습니다. 그 설정 없이 F를 돌리면 오류가 약 1% 나고 처리량도 절반 정도였습니다(04 참고).

**읽는 법**
- **B − A ≈ +1.8ms**: 캐시를 조회하고 저장하는 추가 비용입니다. 첫 요청은 캐시가 없을 때보다 조금 느립니다.
- **D 90%**: p50은 0.3ms인데 p95는 50ms입니다. 꼬리 지연은 miss 10%가 결정합니다. 평균이나 중앙값만 보면 이게 안 보입니다.
- **E**: 동시 요청 200개가 같은 키를 찾습니다. single-flight가 켜져 있으면 원본 호출이 1번, 꺼져 있으면 200번입니다.
- **F**: executor 1개 구조의 상한입니다. CPU 코어 하나로 초당 약 3만 건을 처리합니다.

## 예상 질문과 답

**Q. 원본 갱신 → 캐시 삭제 순서면 완전히 안전한가요?**
아닙니다. 드물지만 이런 경우가 남습니다. 읽기가 원본 갱신 **전에** 옛 값을 읽어 들고 있다가, 캐시 삭제가 끝난 **뒤에** 그 옛 값을 캐시에 씁니다. 그래서 TTL이 마지막 방어선입니다.

**Q. 왜 p99를 보나요?**
사용자 100명 중 1명이 겪는 응답 시간입니다. 캐시 miss, GC 멈춤처럼 가끔 생기는 지연은 평균에 묻히고 p99에서만 드러납니다.
