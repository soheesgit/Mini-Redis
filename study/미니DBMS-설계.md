# 미니 DBMS 설계

> 구현 전 설계 문서. Phase마다 필요한 절만 읽고, 결정이 바뀌면 이 파일을 고친다.
> 표시: **[확정]** 함께 정한 것 · **[제안]** Claude가 낸 안, 아직 확인 전 · **[미정]** 정해야 함

---

## 0. 개요

| Phase | 과제 요구 | 이 설계의 핵심 |
|---|---|---|
| 1 | SQL 처리기 (CLI + 파일 저장), INSERT · SELECT | 렉서 → 파서(AST) → 실행기, 8KB 페이지 + 슬롯, 바이너리 행. **UPDATE · DELETE까지 포함**, WAL로 문장 원자성 보장 |
| 2 | 자동 id에 메모리 B+ 트리 인덱스, 100만 건, 인덱스 vs 선형 탐색 비교 | 인덱스 값 = (페이지, 슬롯) |
| 3 | 스레드 풀 기반 API 서버 | 같은 실행기를 HTTP로 부름 + Mini Redis SELECT 캐시 (API 서버 층) |

**설계 원칙 [확정]**
- 확장성 우선: 과제는 Phase 1에 INSERT · SELECT만 요구하지만 UPDATE · DELETE도 Phase 1에 넣는다. 버퍼 풀은 나중에 붙일 수 있는 구조로 간다.
- 최종 입구는 둘: CLI(Phase 1, 실행기를 직접 부름)와 API 서버(Phase 3, HTTP). CLI는 Phase 3 뒤에도 남는다.
- MySQL은 참고 기준일 뿐: SQL 모양과 타입 이름은 익숙하게 MySQL과 비슷하게 두되, 우리 설계에서 이점이 없는 MySQL 동작은 따르지 않는다.

## 1. Phase 1 — SQL 처리기

### 1.1 문법 [확정: 표준 SQL(MySQL)만]

표준 SQL(MySQL 명령 모양)만 받는다. 파이썬식 표현(`==`, `True`, `None` 등)은 받지 않는다.

```sql
CREATE TABLE users (name VARCHAR(20), age INT);
INSERT INTO users VALUES ('kim', 20);
INSERT INTO users VALUES ('lee', 31), ('park', 25);   -- 다중 행: 한 문장 = WAL 레코드 하나 (1.12)
SELECT * FROM users WHERE id = 1;
UPDATE users SET age = 21 WHERE name = 'kim';
DELETE FROM users WHERE age < 20;
```

- 테이블은 `CREATE TABLE`로 정의한다 [확정]. 스키마는 그 테이블 파일의 0번 메타 페이지에 저장 (1.4)
- 키워드는 대소문자 무관 (`select`, `TRUE`, `null` 모두 같음)
- 문자열 이스케이프는 `''`만, `\`는 일반 글자 (ANSI 방식, MySQL 기본과 다름)
- 식별자는 대소문자 무관으로 비교하고 쓴 모양은 보존, 테이블 파일 이름은 소문자 (MySQL 칸 이름과 같음). 대소문자를 맞추는 글자는 **ASCII A-Z뿐**이다: 켈빈 기호 K(U+212A)·Ω(U+2126)·ı·ſ를 k·ω·i·s로 바꾸면 다른 이름이 같은 파일로 합쳐지기 때문
- 모든 문장은 `;`로 끝난다 (MySQL CLI와 같음). 빈 문장(`;;`, `;`만)은 에러
- INSERT 칸 목록(`INSERT INTO t (a, b)`)은 없다: 값은 id를 뺀 모든 칸 순서대로
- UPDATE `SET` 값은 리터럴만 (`age = age + 1` 같은 계산식 없음)
- 비교 연쇄(`a = 1 = 2`, `a < b < c`)는 에러. 비교·BETWEEN·IN·LIKE·IS의 피연산자는 **값이나 칸만**이고, 괄호는 조건을 묶을 때만 쓴다 (`(a = 1) = TRUE`, `a IN ((b OR c))`는 에러)
- 괄호·NOT 중첩은 200단계까지. 넘으면 문법 에러 (재귀 파서가 스택을 넘쳐 서버 워커가 죽지 않게)
- 칸 정의: `NULL`을 적어도 된다(적지 않은 것과 같음). `DECIMAL`은 `DECIMAL(10,0)`, `DECIMAL(p)`는 `DECIMAL(p,0)` (MySQL 기본값). `INT(11)` 같은 표시 폭은 지원하지 않음
- 같지 않음은 `<>`와 `!=` 둘 다 받는다 (MySQL도 둘 다 지원)
- WHERE가 없는 UPDATE · DELETE는 전체 행에 적용 (MySQL과 같음)
- **id 칸 [확정]**: 모든 테이블 맨 앞에 `id INT`가 자동으로 붙는다. `CREATE TABLE`에 적지 않고, INSERT `VALUES`에서도 뺀다. 값은 nextId로 자동 부여. `SELECT *`에는 나온다. 수정(`SET id = ...`)은 거부
- **칸별 `NOT NULL` [확정]**: 지원 (`CREATE TABLE t (name VARCHAR(20) NOT NULL, ...)`). id는 항상 NOT NULL
- **WHERE 범위 [확정: 전부]**: 비교(`= <> != < <= > >=`), `AND OR NOT`, 괄호, `BETWEEN`, `IN`, `LIKE`(`%`, `_`), `IS [NOT] NULL`. 우선순위는 MySQL과 같이 비교 > `NOT` > `AND` > `OR` (`NOT a = 1`은 `NOT (a = 1)`)
- **`ORDER BY`, `LIMIT` [확정: 지원]**: 결과를 메모리에서 정렬하고 자른다

### 1.2 처리 흐름

```
SQL 문자열 ─▶ 렉서 ─▶ 토큰 목록 ─▶ 파서 ─▶ AST ─▶ 실행기 ─▶ 페이지 읽기/쓰기 ─▶ 결과
```

| 단계 | 하는 일 | 잡는 에러 |
|---|---|---|
| 렉서 (Lexer) | 글자를 토큰으로 자름. 따옴표 안은 통째로 문자열 하나 | 닫히지 않은 따옴표, 모르는 글자 |
| 파서 (Parser) | 토큰 순서를 문법과 대조해 AST 생성 | `FROM` 누락, `;` 누락 |
| 실행기 (Executor) | AST대로 테이블을 읽고 · 쓰고 · 고치고 · 지움, 인덱스를 쓸지 고름 | 없는 테이블, 칸 개수 · 타입 불일치 |
| WHERE 평가기 | 행 하나에 대해 조건식을 계산 (SELECT · UPDATE · DELETE가 같이 씀). 결과는 참 / 거짓 / 알 수 없음(NULL) | 비교할 수 없는 타입끼리 비교 |

- 여러 문장이 오면 **전부 파싱한 뒤 실행**한다. 하나라도 문법이 틀리면 아무것도 실행하지 않음.
- 타입이 늘어서 렉서가 추가로 읽어야 할 것: 소수점 숫자(`3.14`), 비교 연산자(`= <> != < <= > >=`).
- 날짜는 MySQL처럼 문자열 `'2026-11-17'`로 받고, **값 검사 단계**에서 칸 타입이 DATE면 변환한다.
- 숫자도 렉서는 글자 그대로(`"3.14"`) 토큰에 담고, 값 검사 단계에서 칸 타입에 맞춰 변환한다 [제안]. 렉서가 double로 바꾸면 DECIMAL의 정확한 값이 깨지기 때문.

### 1.3 타입 [확정]

| 타입 | 저장 크기 | 저장 방식 | 비고 |
|---|---|---|---|
| `INT` | 4B | 부호 있는 정수 | 약 ±21억 |
| `BIGINT` | 8B | 부호 있는 정수 | `LONG`은 MySQL에서 `MEDIUMTEXT`라 쓰지 않음 |
| `DOUBLE` | 8B | IEEE 754 | 근사값 (`0.1 + 0.2 ≠ 0.3`) |
| `DECIMAL(p,s)` | 8B | 값 × 10^s 를 정수로 (`12.34`, s=2 → `1234`) | 정확한 값. p ≤ 18 |
| `BOOLEAN` | 1B | 0 / 1 | |
| `VARCHAR(n)` | 2B + 가변 | 2B 길이 + UTF-8 바이트. n은 **글자 수** | 행 한도 1.6 참고 |
| `DATE` | 4B | 1970-01-01부터 지난 일수 | MySQL은 3B 형식, 우리는 단순하게 |
| `DATETIME` | 8B | 1970-01-01 00:00:00부터 지난 마이크로초 | **시간대 없음**: 넣은 숫자 그대로 저장 · 반환 |
| `TIMESTAMP` | 8B | UTC 기준 마이크로초 | 입력 · 출력은 **서버 OS 시간대**로 변환. 8B라 2038년 제한 없음 |
| NULL | 0B | 행 앞 비트맵에 표시, 값 바이트 생략 | 허용 (`NOT NULL` 칸은 거부) |

- 바이트 순서: **빅엔디언** 고정 [제안]
- `TEXT` / `BLOB`은 지원하지 않는다 [확정]. 오버플로 페이지가 필요해 행 형식과 페이지 종류가 바뀌기 때문. 긴 글은 `VARCHAR`(최대 약 2040자, 1.6)로
- `VARCHAR2`(Oracle 전용, `''`를 NULL로 취급)는 지원하지 않는다. 우리는 `''`와 NULL을 구분한다.
- 접속별 시간대 변경(`SET time_zone`)은 이번 범위에서 뺌.

### 1.4 파일 구조 [확정: 8KB 페이지]

```
users.db
┌─ 0번 페이지 ─┬─ 1번 페이지 ─┬─ 2번 페이지 ─┬ …
│ 메타         │ 데이터       │ 데이터       │
└──────────────┴──────────────┴──────────────┴ …
N번 페이지의 파일 위치 = N × 8192
```

**0번 메타 페이지 [제안]**

| 위치 | 크기 | 필드 |
|---|---|---|
| 0 | 4B | 매직 `"MDB1"` (다른 파일을 잘못 열었는지 확인) |
| 4 | 2B | 형식 버전 |
| 6 | 2B | 페이지 크기 (8192) |
| 8 | 2B | 칸 개수 |
| 10 | … | 칸마다: 이름 길이 1B + 이름 + 타입 코드 1B + 인자1 2B(n 또는 p) + 인자2 1B(s) + flags 1B(bit0 = NOT NULL) |

스키마를 데이터와 같은 파일에 두는 이유: 두 파일이 서로 어긋날 일이 없음.

### 1.5 데이터 페이지 (8192B) [확정: 헤더 + 앞쪽 슬롯 + 뒤쪽 행]

```
0        16                                              free_end         8192
┌────────┬─────────────────────┬────────────────────────┬─────────────────┐
│ 헤더   │ 슬롯0 슬롯1 슬롯2 → │       빈 공간          │ ← 행2 행1 행0   │
└────────┴─────────────────────┴────────────────────────┴─────────────────┘
          ↑ 16부터              ↑ free_start
빈 공간 = free_end − free_start
```

**헤더 16B**

| 위치 | 크기 | 필드 | 왜 |
|---|---|---|---|
| 0 | 4B | page_id | 엉뚱한 위치를 읽었는지 확인 |
| 4 | 2B | slot_count | 슬롯 개수 |
| 6 | 2B | free_start | 다음 슬롯을 쓸 위치 (빈 페이지: 16) |
| 8 | 2B | free_end | 마지막으로 쓴 행의 시작 (빈 페이지: 8192) |
| 10 | 2B | flags | 페이지 종류 (확장용) |
| 12 | 4B | checksum | CRC32 (이 4B는 0으로 두고 계산). 찢어진 페이지 감지 |

checksum이 필요한 이유: 8KB DB 페이지는 4KB OS 페이지 두 장이라, 쓰다가 죽으면 반만 새 내용인 페이지가 생길 수 있다.

**슬롯 4B (고정 크기)**

| 크기 | 필드 | 설명 |
|---|---|---|
| 2B | offset | 페이지 안 행 시작 위치. **0 = 삭제됨** (번호는 유지) |
| 2B | length | 행 길이 |

- i번 슬롯 위치 = `16 + i × 4` (고정 크기라 계산으로 바로 찾음)
- 2B로 충분한 이유: 오프셋 0~8191, 길이 최대 8172 모두 65535 이하
- 길이가 필요한 이유: VARCHAR와 NULL 때문에 같은 테이블이라도 행 길이가 다름
- 삭제 시 슬롯을 빼지 않는 이유: 뒤 슬롯 번호가 바뀌면 인덱스의 (페이지, 슬롯)이 틀어짐

**행을 뒤에서부터 채우는 이유:** 슬롯표와 행이 각각 얼마나 커질지 미리 모른다. 양 끝에서 마주 보며 채우면 가운데 빈 공간을 경계 없이 다 쓸 수 있다. 둘 다 앞에서 채우면 슬롯 자리를 미리 정해야 해서 남거나 모자란다.

### 1.6 행 배치 [확정: 바이너리, 스키마 순서]

```
[ NULL 비트맵 ][ 칸0 ][ 칸1 ][ 칸2 ] …      ← 칸 순서 = 스키마 순서
```

- 비트맵: `ceil(칸 수 / 8)` 바이트. i번 칸이 NULL이면 i번 비트 = 1, 그 칸의 값 바이트는 쓰지 않음.
- 읽을 때는 스키마 순서대로 앞에서부터 읽는다. 가변 길이 칸은 앞의 2B 길이를 보고 건너뜀.

**예시** `users(id INT, name VARCHAR(20), age INT)` 에 `(1, 'kim', 20)`

```
00 | 00 00 00 01 | 00 03 6B 69 6D | 00 00 00 14        = 14바이트
비트맵  id=1        길이3  k  i  m     age=20
```

빈 페이지에 넣으면:

| 항목 | 값 |
|---|---|
| 행 위치 | 8192 − 14 = **8178** (8178~8191을 씀. 헤더는 반대편 0~15) |
| 슬롯0 | (8178, 14), 위치 16~19 |
| free_start | 16 → 20 |
| free_end | 8192 → 8178 |
| 남은 공간 | 8178 − 20 = 8158 |

**행 한도 (VARCHAR 제한) [확정]**

```
행 최대 = 8192 − 16(헤더) − 4(슬롯) = 8172바이트

테이블 정의 시: 비트맵 + Σ(각 칸 최대 크기) ≤ 8172 아니면 정의 거부
  → 어떤 INSERT도 페이지 하나를 넘지 않음이 보장됨

칸 최대 크기: INT 4 · BIGINT 8 · DOUBLE 8 · DECIMAL 8 · BOOLEAN 1
            DATE 4 · DATETIME 8 · TIMESTAMP 8
            VARCHAR(n) = 2 + 4n   (UTF-8 한 글자 최대 4B)

예: users(id INT, name VARCHAR(n), age INT)
    1 + 4 + (2 + 4n) + 4 ≤ 8172  →  n ≤ 2040
```

INSERT 때는 실제 값이 n글자 이내인지 추가로 검사.

### 1.7 INSERT 절차 [제안]

```
① 값 검사      칸 개수, 타입, NULL, VARCHAR 글자 수 (스키마와 대조)
② id 부여      nextId (자동 증가)
③ 행 인코딩    1.6 배치대로 바이트 배열 생성
④ 페이지 선택  마지막 페이지의 빈 공간 ≥ 행 길이 + 4 ? 그 페이지 : 새 페이지
⑤ 페이지 수정  행을 free_end − 길이에, 슬롯을 free_start에, 헤더 갱신, checksum 재계산
⑥ 커밋 · 쓰기  1.12 WAL 순서대로: 로그에 페이지 이미지 → fsync(로그) → 데이터 파일 (페이지 번호 × 8192)
⑦ 인덱스 등록  index.put(id, (페이지, 슬롯))   ← 파일에 쓴 뒤에 (실패 시 거짓 정보 방지)
⑧ nextId + 1   쓰기에 성공한 뒤에만
```

- ④는 마지막 페이지만 본다. 삭제된 슬롯은 다시 쓰지 않는다 (1.10).
- fsync 시점은 1.12: 문장마다 로그만 fsync, 데이터 파일은 체크포인트 때
- **nextId 복원 [확정]**: 시작할 때 모든 데이터 페이지를 훑어 최대 id + 1. 한계: 마지막 id의 행을 지우고 재시작하면 그 id가 다시 쓰인다
- 실행 중에는 지운 id를 다시 쓰지 않는다 (nextId는 줄어들지 않음). 재시작 때의 예외는 아래 nextId 복원 참고

### 1.8 읽기 (페이지, 슬롯) [제안]

```
페이지 읽기 → checksum 확인 → 슬롯 위치 16 + 슬롯×4 → offset 0이면 "삭제됨"
→ offset부터 length만큼 → 스키마 순서대로 디코딩
```

### 1.9 UPDATE 절차 [제안]

**2단계로 나눈다 [제안]: 먼저 전부 모으고 검사한 뒤에 쓴다.**

```
[모으기 단계] 파일은 아직 안 건드림
① 대상 모으기   모든 데이터 페이지 선형 탐색 + WHERE 평가 → (페이지, 슬롯) 목록
                (Phase 2부터 WHERE id = ?는 인덱스)
② 값 검사       대상 전부에 대해 SET 값의 타입, NULL, VARCHAR 글자 수 (id 수정은 거부)
                하나라도 실패하면 아무것도 쓰지 않고 에러
③ 새 행 인코딩

[쓰기 단계]
④ 자리 정하기 (목록의 행마다)
   새 길이 ≤ 예전 길이           → 제자리 덮어쓰기, slot.length 갱신
   같은 페이지 빈 공간 ≥ 새 길이 → free_end 쪽에 새로 쓰고 slot.offset 갱신 (슬롯 번호 유지)
   둘 다 아님                    → 다른 페이지로 옮김 [확정]: 예전 슬롯 삭제 표시 + 같은 id로 마지막 페이지에 삽입
⑤ 커밋 · 쓰기  checksum 재계산 후 1.12 WAL 순서대로
⑥ (Phase 2)   다른 페이지로 옮겼으면 index.put(id, 새 위치)
```

- 왜 먼저 모으나: (1) 50번째 행에서 값 검사가 실패해도 앞 49행이 이미 바뀌어 있는 일을 막는다. (2) 탐색하면서 행을 뒤 페이지로 옮기면 탐색이 그 행을 다시 만나 두 번 고치게 된다.
- 왜 "자리 없으면 거부"가 아닌가: INSERT가 페이지를 꽉 채우고 다음 페이지로 넘어가므로, 마지막 페이지가 아니면 길어지는 UPDATE가 거의 다 거부된다.
- 짧아지거나 옮겨지면 예전 바이트 일부가 **죽은 공간**(아무 슬롯도 가리키지 않는 바이트)으로 남는다. 처리는 1.10과 같다.
- 같은 페이지 안에서 옮기면 슬롯 번호가 그대로라 인덱스를 고칠 필요가 없다 (페이지 + 슬롯 설계를 고른 이유).

### 1.10 DELETE 절차 [제안]

```
① 대상 모으기  UPDATE ①과 같음 (먼저 전부 모은 뒤 지움)
② 슬롯 표시    slot.offset = 0 (슬롯 번호는 유지)
③ 커밋 · 쓰기  checksum 재계산 후 1.12 WAL 순서대로
④ (Phase 2)   index.remove(id)
```

- 행 바이트는 지우지 않아 죽은 공간이 된다.
- **죽은 공간 처리 [확정: 슬롯 재사용 안 함, 필요할 때만 당겨 모음]** — 검토한 선택지:
  - 버려 둠: 가장 단순. 지우고 넣기를 반복하면 파일만 커짐
  - 같은 페이지 안에서 당겨 모음(compaction): 행을 뒤쪽으로 다시 붙이고 slot.offset만 고침. 슬롯 번호가 그대로라 인덱스 영향 없음
  - 삭제된 슬롯 재사용: 슬롯표가 덜 커짐. 대신 같은 (페이지, 슬롯)이 다른 행을 가리키게 되므로 인덱스에서 먼저 지워야 함
  - 결정: 슬롯 재사용은 하지 않고, 당겨 모음은 "빈 공간 합은 충분한데 연속 공간이 모자랄 때"(UPDATE ④)만 한다.

### 1.11 한계와 실패 동작

- **문장 원자성은 크래시에도 보장한다** [확정: 사용자 결정]. 값 검사 실패는 1.9의 2단계로 막고, 쓰기 단계 도중 크래시는 **WAL**(1.12)로 막는다. 한 문장이 바꾼 페이지는 크래시 뒤에 전부 반영되거나 전부 안 반영된다.
- **INSERT는 마지막 페이지만 본다.** 앞 페이지의 빈 공간은 UPDATE만 쓰므로 파일 크기는 줄지 않는다.
- **checksum이 깨진 페이지** [확정]: 테이블을 열 때 WAL 복구(1.12)를 먼저 한다. 찢어진 페이지가 로그에 있으면 그 이미지로 고쳐진다. 복구 뒤에도 깨진 페이지가 있으면 **테이블 열기를 거부**하고 페이지 번호를 에러에 담는다 (모르는 사이에 데이터가 빠지는 것을 막음). Phase 2 인덱스 재구축도 복구 뒤에 한다.

### 1.12 WAL과 복구 [확정: redo 전용, 페이지 이미지, 문장 단위]

**규칙 두 개** (WAL = Write-Ahead Log, 먼저 로그에 쓰기)
1. 데이터 파일의 페이지는 **그 변경을 담은 로그가 디스크에 간 뒤에만** 쓴다.
2. 문장의 성공 응답은 **로그 fsync가 끝난 뒤에** 한다. 이 순간이 커밋이다.

**방식**
- **redo 전용 + no-steal**: 커밋 전 페이지는 메모리에만 있고 데이터 파일에 가지 않는다. 그래서 크래시 뒤 "되돌리기(undo)"가 필요 없고, 커밋된 것을 "다시 하기(redo)"만 한다.
- **물리 로그(페이지 이미지)**: 로그에 "무슨 SQL을 했나"가 아니라 **바뀐 페이지 8KB 통째**를 담는다. 같은 이미지를 몇 번 덮어써도 결과가 같아(멱등) 복구가 단순하고, 반쯤 쓰다 찢어진 데이터 페이지도 이 이미지로 고쳐진다. (Mini Redis AOF는 명령을 적는 논리 로그라 다르다)
- **원자성 단위 = 문장 하나** (autocommit). `BEGIN` / `COMMIT` / `ROLLBACK`으로 여러 문장을 묶는 트랜잭션은 이번 범위 밖 [제안: 확장]
- **로그 파일은 테이블마다** `users.wal`. 한 문장은 한 테이블만 바꾸고, Phase 3의 테이블 락과 범위가 같아 로그끼리 경쟁하지 않는다.

**레코드 = 문장 하나**

```
[ 길이 4B ][ txid 8B ][ 페이지 수 n 2B ][ (페이지 번호 4B + 페이지 이미지 8192B) × n ][ CRC32 4B ]
```

- CRC가 맞는 레코드 = 끝까지 다 쓰인 레코드 = 커밋된 문장. 따로 COMMIT 표시를 두지 않는다.
- CRC 범위는 **길이 필드부터 마지막 이미지까지**. 길이 = 레코드 전체 바이트 = `14 + n × 8196 + 4`
- 읽을 때 길이부터 검사: 위 식과 다르거나 남은 파일 크기보다 크면 찢어진 꼬리로 본다 (쓰레기 길이로 수 GB를 할당하는 일 방지)
- 새 페이지(INSERT로 파일 끝에 붙는 페이지)도 이미지로 같이 담는다.

**쓰기 순서 (INSERT · UPDATE · DELETE 공통, 1.7 ⑥ · 1.9 ⑤ · 1.10 ③)**

```
① 바뀔 페이지들을 메모리에서 새 이미지로 만듦 (checksum 포함)   ← 1.9의 2단계 덕분에 다 모인 상태
② 로그 끝에 레코드 하나 append
③ fsync(로그)                                                    ← 커밋. 여기서 죽으면: 레코드가 다 갔으면 반영, 아니면 없던 일
④ 데이터 파일에 페이지들 쓰기 (fsync 안 함)                      ← 여기서 죽어도 로그에 있으니 복구가 다시 씀
⑤ 성공 응답 · (Phase 2) 인덱스 갱신 · nextId 갱신
```

**복구 (테이블을 열 때마다)**

```
로그를 앞에서부터 읽음
  CRC 맞음  → 레코드의 페이지 이미지들을 데이터 파일에 덮어씀
  CRC 틀림 / 길이 모자람 → 찢어진 꼬리. 여기서 멈추고 그 뒤를 잘라 냄
fsync(데이터 파일) → 로그 비우기(길이 0) → fsync(로그)
→ checksum 검사 (1.11) → nextId 복원 (1.7) → (Phase 2) 인덱스 재구축
```

**체크포인트**: 로그가 16MB를 넘거나 테이블을 닫을 때 `fsync(데이터 파일) → 로그 비우기`. 둘 사이에 죽어도 다음 복구가 같은 이미지를 다시 쓸 뿐이라 안전하다.
- **쓰기 락을 잡은 스레드가 ④ 뒤에만** 한다. 다른 스레드가 ③과 ④ 사이에 있을 때 로그를 비우면, 데이터에 아직 안 쓴 커밋을 잃기 때문 (3절)
- 로그 파일은 지우지 않고 길이 0으로 자르기만 한다

**쓰는 도중 I/O 실패 (디스크 가득 등)**
- ② · ③ 실패: 로그를 이번 레코드 시작 위치로 잘라 되돌리고 에러 응답. 반쪽 레코드 뒤에 다음 커밋이 붙으면 복구가 반쪽에서 멈춰 그 뒤 커밋을 잃기 때문
- 자르기도 실패하거나 ④에서 실패: **fail-stop** — 그 테이블을 닫고 다시 열어 복구를 돌린다 (로그에 커밋된 것이 반영되고 nextId · 인덱스도 다시 맞춰짐)
- fsync 실패는 재시도하지 않는다 (재시도 성공이 데이터가 디스크에 갔다는 뜻이 아님)

**`CREATE TABLE`**: 로그 대신 `users.db.tmp`에 메타 페이지를 쓰고 fsync → 이름을 `users.db`로 바꿈(rename은 한 번에 일어남) → **디렉터리 fsync**. 빈 `users.wal`도 이때 같이 만든다 (이미 있으면 길이 0으로). 시작할 때 남은 `.tmp`는 지운다.
- 디렉터리 fsync가 필요한 이유: 새 파일 · 이름 바꾸기는 디렉터리 항목의 변경이라, 디렉터리를 fsync하지 않으면 전원 차단 뒤 파일 자체가 사라질 수 있다
- `.wal`을 첫 문장 때가 아니라 CREATE 때 만드는 이유: 같은 이유로 첫 커밋을 잃지 않게, 그리고 옛 테이블의 로그가 새 테이블에 재생되지 않게

**fsync 옵션**: 기본은 문장마다 로그 fsync. 끄는 옵션(`--fsync=off`)은 **③의 로그 fsync만** 끈다 (체크포인트 · 복구의 fsync와 디렉터리 fsync는 항상 함. 이것까지 끄면 전원 차단 뒤 찢어진 페이지를 고칠 로그가 없어 테이블 자체를 못 연다). 그리고 끄면 **프로세스 크래시**에는 여전히 원자적이지만 **전원 차단**에는 보장하지 않는다고 README에 적는다. 100만 건 적재는 다중 행 INSERT(`VALUES (...), (...), ...`)로 문장 수를 줄여 fsync 횟수를 줄인다.

**한계 [확정]**: 한 문장이 바꾸는 페이지는 커밋 전까지 메모리에 들고 있다. 100만 건 전체 UPDATE면 약 2,200페이지(약 18MB)라 감당 가능한 크기로 본다.
- macOS에서 `FileChannel.force()`가 드라이브 캐시까지 내리는지는 확인하지 않았다 [미검증]. 프로세스 크래시는 영향이 없고 전원 차단에만 해당

## 2. Phase 2 — B+ 트리 인덱스

리프의 각 항목은 자동 ID와 행 위치를 담는다. 위치는 `((long) page << 16) | slot`으로 묶으며, 슬롯은 하위 16비트에 들어간다. 내부 노드는 자식의 최소 ID를 분리 키로 사용한다. ID 이하의 분리 키 중 가장 큰 값에 해당하는 자식으로 내려가고, 그런 값이 없으면 첫 자식으로 내려간다.

기본 용량은 리프당 키 64개, 내부 노드당 자식 65개다. 용량을 초과하면 절반을 오른쪽 형제로 옮기고 부모에 새 자식을 추가한다. 삭제 후 항목 수가 최소 점유율(최대 용량의 절반을 올림) 아래로 내려가면 형제에게서 하나를 옮긴다. 두 형제 모두 여유가 없으면 두 노드를 합친다. 루트에 자식 하나만 남으면 그 자식이 루트가 된다. 범위 조회는 시작 ID가 들어갈 리프를 찾은 뒤 다음 리프 링크를 따라간다.

`Table`은 WAL 복구가 끝난 뒤 데이터 페이지를 한 번 순회해 인덱스와 `nextId`를 구성한다. 삭제된 슬롯은 건너뛴다. 커밋 성공 후에 INSERT와 다른 페이지로 옮겨진 UPDATE의 위치를 기록하고, DELETE의 ID를 제거한다. 같은 페이지 안에서 행의 바이트 위치만 바뀌면 슬롯 번호는 그대로다.

실행기는 먼저 WHERE를 검증한다. ID와 INT 범위 정수를 비교하는 `=`, `<`, `<=`, `>`, `>=`, `BETWEEN` 조건은 인덱스를 사용한다. 나머지 조건은 선형 탐색한다. 인덱스가 반환한 행에도 원래 WHERE를 적용하며, 범위 조회는 후보를 페이지·슬롯 순서로 방문해 선형 탐색과 결과 순서를 맞춘다. [100만 건 비교 실험](../mini-dbms/README.md#100만-행-벤치마크)

## 3. Phase 3 — API 서버 + 스레드 풀 + Redis 캐시

- 고정 크기 스레드 풀이 요청마다 스레드를 배정하고, 그 스레드가 실행기를 직접 부른다 [제안]
- 동시성: 처음엔 테이블 단위 읽기/쓰기 락 (SELECT끼리 동시에, INSERT · UPDATE · DELETE는 혼자) [제안]. 페이지 단위 락은 확장 시
- 락 하나가 **파일 + 메모리 B+ 트리 + nextId를 함께** 감싼다 [제안]. B+ 트리는 여러 스레드가 동시에 고치면 깨지기 때문
- UPDATE · DELETE는 **모으기(1.9 ①)부터 커밋 뒤 갱신(1.12 ⑤)까지 쓰기 락 하나**로 감싼다. 읽기 락으로 모은 뒤 쓰기 락으로 올리면 `ReentrantReadWriteLock`에서 자기 자신과 데드락이고, 풀었다 다시 잡으면 모은 (페이지, 슬롯)이 낡는다
- 체크포인트도 쓰기 락 안에서만 (1.12)
- 테이블 열기(복구 포함)는 테이블마다 **한 번만** (`ConcurrentHashMap.computeIfAbsent`). 두 스레드가 동시에 열면 복구가 두 번 돌거나 로그를 비우는 중에 다른 쪽이 쓴다
- 페이지 읽기는 위치를 지정하는 `FileChannel.read(buf, pos)`만 쓴다. 채널 하나를 `seek` + `read`로 같이 쓰면 다른 스레드가 위치를 바꿔 엉뚱한 페이지를 읽는다
- **[미정]** 요청 · 응답 형식 (예: `POST /query` 본문에 SQL, JSON 응답), 에러 코드, 본문 크기 제한, 스레드 풀 크기

**Mini Redis 캐시 [확정: cache-aside, API 서버 층에서 호출]**

```
SELECT   API 서버 ─▶ Redis GET ──hit──▶ 응답
                         └──miss─▶ 실행기 ─▶ Redis SET ─▶ 응답

쓰기     API 서버 ─▶ 실행기 (결과에 바뀐 테이블 이름) ─▶ 그 테이블 캐시 무효화 ─▶ 응답
```

- 실행기는 Redis를 모른다 → Phase 1 · 2를 Redis 없이 테스트할 수 있고, Redis 장애가 엔진에 번지지 않음
- Redis가 꺼져 있거나 느리면 캐시 없이 실행기로 바로 간다 (응답은 정상)
- CLI는 실행기를 직접 불러 캐시를 거치지 않는다 → **서버가 도는 동안 CLI로 같은 데이터 폴더에 쓰지 않는다** (CLI 쓰기는 캐시를 못 지우고, 서버의 테이블 락도 못 막음). 규칙만 두지 않고 데이터 폴더에 잠금 파일(`FileChannel.tryLock`)을 둬서, 서버가 떠 있으면 CLI가 시작을 거부하게 한다 [제안]
- 무효화는 **테이블별 버전 번호를 키에 넣는 방식** [제안]. 소희 구현과 같은 방식이고, 클라이언트가 GET / PUT(ttl) / INCR만 있어 패턴 삭제가 없으므로 추가 구현 없이 되는 유일한 안
  - 키 예: `dbms:{테이블}:v{버전}:{SELECT 문 해시}`. 쓰기 뒤 그 테이블 버전을 `INCR`
  - 버전은 **실행기를 부르기 전에** 읽는다. 그래야 SELECT와 쓰기가 겹쳐도 옛 결과가 새 버전 키에 들어가지 않음
  - TTL은 필수: 쓰기 때 `INCR`이 실패(Redis 장애)하면 버전이 안 올라가, Redis가 돌아온 뒤 옛 값이 나올 수 있음. TTL이 그 시간을 제한함
  - 서버가 시작해 테이블을 열 때 그 테이블 버전을 `INCR`한다. 로그 fsync 뒤 `INCR` 전에 죽었으면, 재시작 뒤 커밋 전 결과가 캐시에서 나올 수 있기 때문
- **[미정]** TTL 길이, Redis 연결 시간 제한, 결과가 너무 크면 SET 건너뛰기 기준
- 참고 구현: 소희 `team-dbms` 브랜치의 `mini-dbms/src/main/java/minidbms/cache/RedisCache.java` (Mini Redis HTTP API `/keys/{key}`)

## 5. 결정 기록

| 결정 | 이유 |
|---|---|
| 바이트 오프셋 append 대신 페이지 + 슬롯 | UPDATE · DELETE 시 행이 옮겨져도 인덱스 유지, 페이지 단위 캐시 가능 |
| 페이지 8KB | 사용자 결정 (PostgreSQL 기본과 같음) |
| 인덱스가 오프셋이 아닌 슬롯 번호를 가짐 | 페이지 안에서 행이 옮겨지면 슬롯표 한 칸만 고치면 됨 |
| 행은 뒤에서, 슬롯은 앞에서 | 슬롯 수와 행 크기 비율을 몰라도 빈 공간을 다 씀 |
| 바이너리 행, 스키마 순서 | 길이 계산이 정확해야 페이지 빈 공간 관리 가능, 칸 위치가 스키마로 정해짐 |
| 표준 SQL(MySQL)만, 파이썬식 표현 제거 (A안 철회) | 사용자 결정. 문법이 하나라 렉서 · 파서 · 테스트가 단순. `!=`는 MySQL도 지원해 유지 |
| Phase 1에 UPDATE · DELETE 포함 | 사용자 결정. 페이지 + 슬롯 설계가 이미 행 이동 · 삭제를 대비함 |
| `CREATE TABLE` 지원 | 사용자 결정. 스키마를 0번 메타 페이지에 두는 설계와 맞고, 테스트를 SQL만으로 쓸 수 있음 |
| id는 `id INT` 자동 추가, 수정 거부 | 과제가 자동 id. 100만 건은 INT로 충분. id는 인덱스 키라 바뀌면 인덱스를 다시 넣어야 함 |
| `NOT NULL` 지원, `TEXT`/`BLOB` 미지원 | NULL 비트맵이 이미 있어 검사만 추가. 오버플로 페이지는 행 형식을 바꿈 |
| WHERE 전부 + `ORDER BY` · `LIMIT` | 각각 작고, 개발 시간이 짧음 (사용자 결정) |
| 길어진 UPDATE는 다른 페이지로 옮김, 슬롯 재사용 안 함 | 거부하면 마지막 페이지 밖에서 거의 다 실패. 슬롯 재사용은 같은 (페이지, 슬롯)이 다른 행을 가리키는 버그 위험 |
| nextId는 최대 id + 1 | 추가 쓰기 없음, Phase 2 재구축 스캔에서 같이 구함 |
| 키 용량 기본 64, 생성자로 조정 | 작은 용량의 테스트에서 분할, 병합, 루트 높이 변화를 적은 행으로 재현 |
| 리프에 다음 리프 링크 저장 | 시작 위치를 찾으면 연결을 따라 범위 내의 ID를 순서대로 읽음 |
| 삭제 후 형제 간 재배치와 병합 | 노드 점유율과 모든 리프의 같은 깊이를 유지 |
| `Table`이 인덱스를 소유 | WAL을 복구하고 다음 ID를 계산하는 순회에서 함께 재구축 |
| 크래시에도 문장 원자성 보장 (WAL 도입) | 사용자 결정. 원자성 없이 두면 여러 페이지에 걸친 UPDATE · DELETE가 반만 남는 문제가 실제로 생김 |
| WAL은 redo 전용 · 페이지 이미지 · no-steal | 커밋 전 페이지는 데이터 파일에 안 쓰므로 undo가 필요 없음. 복구는 이미지 덮어쓰기라 여러 번 해도 결과가 같고, 찢어진 페이지도 고침 |
| 로그 fsync는 문장마다 (기본 켬), 데이터 fsync는 체크포인트 때 | 커밋 = 로그가 디스크에 있음. 100만 건 적재는 다중 행 INSERT로 fsync 횟수를 줄임 |
| Redis 캐시는 API 서버 층에서 호출 (실행기 안 아님) | 엔진이 외부 서비스에 의존하지 않음, 실무 cache-aside 구조와 같음. 무효화는 실행기가 바뀐 테이블 이름을 돌려줘서 해결 |
| BIGINT (LONG 아님) | MySQL에서 LONG = MEDIUMTEXT |
| TIMESTAMP는 UTC 저장 + 서버 시간대 변환, DATETIME은 변환 없음 | MySQL과 같은 의미 |
| CHAR 미지원 | UTF-8에선 CHAR도 길이 + 바이트로 저장해야 해서 VARCHAR와 이점 차이가 없음. MySQL 호환만을 위해 두지 않음 |
| VARCHAR2 미지원 | Oracle 전용, `''` = NULL 동작이 MySQL과 다름 |
