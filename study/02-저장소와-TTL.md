# 02. 저장소와 TTL ★★ (0.5시간)

**한 줄 답**: 모든 명령은 `Store.execute()` 하나로 들어옵니다. 만료는 **조회할 때 검사**하고, **100ms마다 무작위 샘플로 청소**하는 두 가지로 처리합니다.

> 흐름: executor가 명령을 꺼냄 → **[Store.execute: 찾기·만료 검사·변경·AOF 레코드 만들기]** → AOF write

## 꼭 알 것 3가지

**1. 입구는 하나**
HTTP 요청, AOF 재실행, 단위 테스트가 모두 `execute()`를 부릅니다. 그래서 저장소 로직이 한 곳에만 있습니다.

**2. 만료는 두 가지 방법을 같이 쓴다**

| 방식 | 언제 | 하나만 쓰면 깨지는 것 |
|---|---|---|
| 조회 시 검사 (`lookup`) | 키를 다루는 모든 명령의 시작 | 이것만 쓰면 아무도 안 읽는 만료 키가 메모리에 계속 남는다 |
| 주기적 청소 (`activeExpireCycle`) | 100ms마다, TTL 키 20개 무작위 검사. 25% 넘게 만료됐으면 반복 (최대 25ms) | 이것만 쓰면 청소 주기 사이에 만료된 값을 돌려준다 |

**3. 시계가 2개**
메모리에서는 `nanoTime`(단조 시계)을 씁니다. 시스템 시간이 바뀌어도 뒤로 가지 않습니다. 파일에는 유닉스 시각을 씁니다. `nanoTime`은 프로세스마다 기준점이 달라서 재시작하면 의미가 없기 때문입니다.

## 예상 질문과 답

**Q. 만료된 값이 반환될 수 있나요?**
없습니다. 키를 다루는 모든 명령이 `lookup`을 거치고, 거기서 만료 여부를 먼저 봅니다.

**Q. 왜 전부 검사하지 않고 20개만 무작위로 보나요?**
전부 보는 건 O(n)이라 키가 많으면 그동안 서버가 멈춥니다. 샘플에서 만료 비율이 높으면 "아직 많이 남았다"고 보고 반복합니다.

**Q. TTL 10초를 줬는데 서버가 5초 꺼져 있었다면요?**
파일에는 "언제 만료되는지"를 절대 시각(유닉스 ms)으로 저장합니다. 그래서 재시작하면 남은 시간은 5초입니다. 꺼진 동안 시스템 시간이 바뀌는 것은 막을 수 없는 한계로 문서에 남겨 두었습니다.

## 건너뛰어도 되는 것
`glob` 패턴 매칭, `INCR`의 정수 검사 정규식은 건너뛰어도 됩니다.
