계좌 이체 한 번으로 보는 DBMS

왜 S3~S5를 깊게 보나. 수업·면접에서 가장 자주 묻고, 이미 아는 것과 바로 이어지기 때문입니다. CS:APP의 페이지·캐시는 버퍼 풀로, Pintos의 lock·동기화는 DBMS 락으로 연결됩니다. 미니 Redis에서 만든 AOF는 S6의 WAL과 같은 생각이라 S6는 짧게 잡았습니다.

S0. 전체 지도

10분

앱이 아래 SQL을 보냈다고 합시다. 7번 계좌(A)에서 1만 원을 빼는 문장입니다. 다음을 눌러 이 문장이 DBMS 안의 누구를 거치는지 따라가 보세요.

UPDATE accounts SET balance = balance - 10000 WHERE id = 7; … COMMIT;

직접 해 보기 · 단계별로 넘기기

키보드 ← → 도 됩니다

이 지도에서 꼭 가져갈 것은 두 가지입니다.

  • 층이 나뉘어 있다. 위층(쿼리 처리기)은 "무엇을 어떻게 찾을지"를 정하고, 아래층(저장 엔진)은 "메모리와 디스크 사이에서 안전하게 옮기는 일"을 합니다.
  • COMMIT 응답은 로그가 디스크에 닿은 뒤에 나간다. 데이터 파일은 나중에 씁니다. 이 순서가 S4·S6의 핵심입니다.
확인 질문: COMMIT에 "성공" 응답이 나간 순간, 데이터 파일에는 새 잔액이 쓰여 있을까?
꼭 그렇지 않습니다. 응답 전에 확실히 디스크에 쓰는 것은 로그입니다. 데이터 파일의 페이지(dirty 페이지)는 나중에 백그라운드에서 씁니다. 그 사이에 장애가 나면 로그로 다시 만듭니다(redo).

S1. DBMS가 왜 필요한가

★5분
용어부터. 데이터베이스(DB)는 모아 둔 데이터 자체, DBMS(Database Management System)는 그 데이터를 관리하는 프로그램(MySQL, PostgreSQL 등)입니다. 일상에서는 둘 다 "DB"라고 부르지만 시험에서는 구분합니다.

은행 앱을 파일 하나(accounts.txt)로 만든다고 생각해 보세요. 처음엔 되지만 곧 이런 문제가 생깁니다.

파일로 직접 하면 깨지는 것예DBMS가 대신 해 주는 것
동시 접근두 프로그램이 같은 줄을 동시에 고쳐 한쪽 수정이 사라짐락·MVCC로 동시성 제어 (S5)
중간 장애A에서 뺀 직후 전원이 나가 돈이 증발트랜잭션·로그로 원자성과 복구 (S4, S6)
검색 코드 중복프로그램마다 "id가 7인 줄 찾기"를 직접 짬SQL 한 줄 + 인덱스 (S2, S3)
형식 변경파일에 열 하나 추가하면 읽는 프로그램이 전부 깨짐데이터 독립성 (아래 3단계 스키마)
중복과 불일치고객 주소가 파일 세 곳에 있고 한 곳만 바뀜정규화된 설계, 제약 조건 (S7)
권한누구나 파일 전체를 읽음사용자별 권한(GRANT)

3단계 스키마와 데이터 독립성

정보처리 자격증에서 본 그 내용입니다. 층을 나눠 두면 한 층을 바꿔도 다른 층이 깨지지 않습니다.

층누가 보는 모습바꿔도 안 깨지는 것
외부 스키마앱·사용자마다 보는 일부 (뷰)개념 스키마에 열을 추가해도 앱이 그대로 동작 → 논리적 독립성
개념 스키마전체 테이블·관계·제약 (DB 설계자)
내부 스키마디스크에 어떻게 저장되나 (페이지, 인덱스)인덱스를 추가하거나 저장 방식을 바꿔도 SQL이 그대로 → 물리적 독립성
확인 질문: 테이블에 인덱스를 새로 만들었는데 앱 코드는 한 줄도 안 바꿔도 된다. 어떤 독립성 덕분인가?
물리적 데이터 독립성. 인덱스는 내부 스키마(저장 방식)의 일입니다. SQL은 "무엇을"만 말하므로, 저장 방식이 바뀌어도 그대로 동작합니다.

S2. 관계형 모델과 SQL

★★10분
"관계(relation)"의 뜻. 일상에서는 "사이·연결"이지만, 관계형 모델에서 relation은 테이블 그 자체를 말합니다. 테이블끼리 이어진다는 뜻이 아닙니다(그건 FK가 합니다).
이론 용어실무 용어예
릴레이션테이블accounts
튜플행(row), 레코드(7, 지호, 100000)
애트리뷰트열(column)balance
도메인열이 가질 수 있는 값의 범위balance는 0 이상의 정수

키: 행을 하나로 짚는 방법

users
id (PK)nameemail
1지호j@ex.com
2민수m@ex.com
accounts
id (PK)user_id (FK)balance

키뜻위 예에서
슈퍼키행을 유일하게 구분하는 열 묶음 (군더더기 있어도 됨)(id), (id, name), (email) …
후보키슈퍼키 중 더 줄일 수 없는 것 (최소성)users의 id, email
기본키 (PK)후보키 중 대표로 고른 하나. NULL 불가, 중복 불가users.id
외래키 (FK)다른 테이블의 PK를 가리키는 열accounts.user_id → users.id

무결성 제약이 키를 지켜 줍니다. PK는 비거나 겹치면 안 되고(개체 무결성), FK는 존재하는 행만 가리켜야 합니다(참조 무결성). users에서 1번을 지우려 하면, 1번을 가리키는 계좌가 남아 있으므로 DBMS가 거부하거나(RESTRICT) 같이 지웁니다(CASCADE). 안 하면? 주인 없는 계좌가 생깁니다.

SQL은 "무엇을"만 말한다

C에서는 "배열을 처음부터 돌면서 id가 7이면 멈춰라"처럼 방법을 씁니다. SQL은 WHERE id = 7처럼 원하는 결과만 씁니다(선언형). 방법은 S0의 옵티마이저가 고릅니다. 그래서 인덱스를 추가하면 같은 SQL이 갑자기 빨라집니다.

분류하는 일명령
DDL (정의)테이블 구조 만들기·바꾸기CREATE ALTER DROP
DML (조작)행 읽기·쓰기SELECT INSERT UPDATE DELETE
DCL (제어)권한, 트랜잭션GRANT REVOKE COMMIT ROLLBACK
확인 질문 1: users에 email이 유일하다면 email은 후보키인가? 기본키가 될 수도 있나?
후보키가 맞습니다(유일하고, 열 하나라 더 줄일 수 없음). 기본키로 고를 수도 있지만 보통은 바뀔 일이 없는 id를 고릅니다. 이메일은 사용자가 바꿀 수 있고, PK가 바뀌면 그걸 가리키는 FK를 모두 고쳐야 하기 때문입니다.
확인 질문 2: accounts에 user_id = 99(없는 사용자)인 행을 넣으려 하면?
FK 제약이 있으면 참조 무결성 위반으로 INSERT가 실패합니다.

S3. 저장 구조: 페이지, 버퍼 풀, 인덱스

★★★15분

출발점은 하나입니다. 디스크는 메모리보다 훨씬 느리다. 저장 엔진의 설계는 거의 다 "디스크를 덜 읽고, 읽을 땐 크게 읽자"에서 나옵니다.

페이지: 디스크와 주고받는 단위

DBMS는 행 하나가 아니라 페이지(블록) 단위로 읽고 씁니다. InnoDB의 기본 페이지 크기는 16KB입니다. 한 페이지에 행이 수십~수백 개 들어갑니다. CS:APP의 가상 메모리 페이지와 이름도, 이유도 같습니다.

버퍼 풀: DBMS가 직접 관리하는 페이지 캐시

상황버퍼 풀이 하는 일
필요한 페이지가 메모리에 있음 (hit)바로 돌려줌. 디스크 안 감
없음 (miss)디스크에서 페이지를 읽어 빈 칸에 올림
빈 칸이 없음오래 안 쓴 페이지를 내보냄 (LRU 계열). dirty면 먼저 디스크에 씀
페이지를 수정함dirty 표시만 하고, 디스크에는 나중에 씀

OS 페이지 캐시가 있는데 왜 따로 두나? DBMS는 "이 페이지는 로그가 디스크에 닿기 전엔 내보내면 안 된다"(WAL 규칙, S6) 같은 순서를 지켜야 합니다. OS는 그걸 모릅니다. 그래서 언제 쓰고 언제 내보낼지를 DBMS가 직접 정합니다.

인덱스: 전체를 읽지 않고 찾기

인덱스가 없으면 WHERE id = 33을 찾으려고 테이블의 모든 페이지를 읽어야 합니다(full scan). 인덱스는 책 뒤의 찾아보기처럼 "33은 이 페이지에 있다"를 알려 주는 별도 구조입니다. 대부분의 DBMS는 기본 인덱스로 B+트리를 씁니다.

직접 해 보기 · B+트리에서 키 찾기
  1. id를 넣고 "찾기"를 눌러 보세요. 33, 15, 34(없는 값)를 차례로 해 보면 좋습니다.
  • 안쪽 노드는 길 안내만 합니다. 키 40이 있으면 "40보다 작으면 왼쪽, 크거나 같으면 오른쪽"입니다.
  • 리프 노드에 실제 키가 다 있고, 리프끼리 옆으로 이어져 있습니다(점선). 그래서 범위 검색은 시작 리프만 찾고 옆으로 쭉 읽으면 됩니다.
  • 노드 하나 = 페이지 하나. 16KB 페이지에 키와 포인터가 수백 개 들어가므로 자식이 수백 개입니다. 자식이 500개씩이면 높이 3에 500³ ≈ 1억 2500만 개 키가 들어갑니다. 1억 행에서도 페이지 3~4개만 읽으면 찾습니다.
B+트리 인덱스해시 인덱스
같은 값 찾기 (=)O(log n), 페이지 3~4개O(1) 평균
범위 (BETWEEN, <, >)됨: 리프를 옆으로 읽음안 됨: 해시는 순서를 버림
정렬 (ORDER BY)이미 정렬돼 있음안 됨
미니 Redis와 연결-직접 만든 해시 테이블과 같은 성질

인덱스의 비용. 읽기는 빨라지지만 INSERT·UPDATE·DELETE 때마다 인덱스도 같이 고쳐야 하고 공간도 듭니다. 그래서 "모든 열에 인덱스"는 답이 아닙니다.

확인 질문 1: 버퍼 풀이 dirty 페이지를 내보내야 할 때, 그냥 버리면 안 되는 이유는?
dirty 페이지에는 디스크에 아직 없는 수정 내용이 있습니다. 버리면 그 수정이 사라지므로 먼저 디스크에 써야 합니다(그리고 WAL 규칙상 그 수정의 로그가 먼저 디스크에 있어야 합니다).
확인 질문 2: "가입일이 2026년 1월~3월인 사용자"를 자주 찾는다. 해시 인덱스와 B+트리 중 무엇을 거나?
B+트리. 범위 조회이기 때문입니다. 해시는 값을 흩어 놓아서 "1월~3월 사이"라는 순서 정보가 없습니다.

S4. 트랜잭션과 ACID

★★★15분
"트랜잭션"의 뜻. 일상에서는 "거래"지만, DBMS에서는 전부 되거나 전부 안 되어야 하는 작업 묶음입니다. 이체의 "A에서 빼기 + B에 더하기"가 한 트랜잭션입니다.

아래에서 이체 도중 전원이 나가는 상황을 만들어 보세요. 트랜잭션이 없을 때와 있을 때 결과가 어떻게 다른지가 핵심입니다. 처음 잔액은 둘 다 100,000원, 합계는 늘 200,000원이어야 합니다.

직접 해 보기 · 이체 도중 장애 내기
전원이 나가는 때:
실행한 순서
    장애 순간 로그 파일에 있던 것
      재시작 후 잔액
      A (7번)
      B (8번)
      합계

      ACID: 트랜잭션이 지켜야 할 네 가지

      성질뜻이체에서누가 지키나
      Atomicity 원자성전부 되거나 전부 안 되거나A만 빠지고 B는 안 더해진 상태가 남지 않음undo 로그 (복구 관리자)
      Consistency 일관성규칙을 지킨 상태 → 규칙을 지킨 상태잔액 ≥ 0, 합계 200,000 유지제약 조건 + 앱의 올바른 로직
      Isolation 격리성동시에 돌아도 서로 중간 상태를 못 봄이체 중간(A만 빠진 순간)을 남이 못 봄락·MVCC (동시성 제어, S5)
      Durability 지속성COMMIT 응답 뒤엔 장애에도 남음"이체 완료" 뒤 전원이 나가도 유지redo 로그 + 커밋 때 fsync (S6)

      C만 성격이 다릅니다. A·I·D는 DBMS가 기계적으로 보장하지만, "합계가 유지돼야 한다"는 규칙은 앱이 올바른 SQL을 짜야 지켜집니다. DBMS는 CHECK·FK 같은 선언된 제약만 검사합니다.

      트랜잭션 상태

      활동 → 부분 완료(마지막 명령 실행) → 완료(COMMIT 로그가 디스크에)
      활동/부분 완료 → 실패 → 철회(ROLLBACK, undo로 되돌림)

      확인 질문 1: "2 끝난 뒤" 장애에서 트랜잭션이 있으면 왜 A가 100,000으로 돌아오나? A가 든 페이지가 이미 디스크에 써졌어도?
      로그에 <T1, A, 100,000 → 90,000>은 있지만 <T1 COMMIT>이 없습니다. 재시작 때 복구 관리자는 "커밋 안 된 트랜잭션"이라고 판단하고, 로그의 이전 값(100,000)으로 되돌립니다(undo). 페이지가 이미 디스크에 써졌어도 로그가 있으니 되돌릴 수 있습니다.
      확인 질문 2: ACID 중 "COMMIT 응답 직후 전원이 나가도 데이터가 남는다"는 무엇이고, 무엇으로 지키나?
      Durability(지속성). 커밋 응답 전에 로그를 디스크에 fsync하고, 재시작 때 그 로그를 다시 적용(redo)해서 지킵니다.

      S5. 동시성: 락, 격리 수준, 이상 현상

      ★★★15분

      트랜잭션을 하나씩 차례로 돌리면(직렬 실행) 안전하지만 느립니다. 그래서 동시에 돌리되 "직렬로 돌린 것과 같은 결과"를 내는 것이 목표입니다. 미니 Redis는 executor 하나로 진짜 직렬 실행을 했고, DBMS는 여러 스레드가 동시에 돌면서 이걸 흉내 냅니다.

      방법 1: 락

      이미 걸린 락 →
      새로 요청 ↓      		S (읽기)X (쓰기)
      S (읽기)같이 가능대기
      X (쓰기)대기대기

      읽기끼리는 함께, 쓰기가 끼면 기다립니다. Pintos의 lock과 같고, 읽기를 함께 허용한다는 점만 다릅니다(reader-writer lock).

      2단계 락킹(2PL): 락을 얻기만 하는 단계 → 풀기만 하는 단계로 나누면 직렬 가능성이 보장됩니다. 보통 커밋 때 한꺼번에 풉니다.

      교착 상태(deadlock). T1이 A를 잡고 B를 기다리고, T2가 B를 잡고 A를 기다리면 영원히 멈춥니다. DBMS는 대기 그래프에서 사이클을 찾아 한쪽을 강제로 ROLLBACK합니다. 그래서 앱은 "트랜잭션 실패 → 재시도"를 준비해야 합니다.

      방법 2: MVCC (다중 버전)

      행을 고칠 때 옛 버전을 지우지 않고 남겨 둡니다. 읽는 쪽은 "내가 볼 수 있는 시점의 버전"을 읽으므로 읽기가 쓰기를 기다리지 않고, 쓰기도 읽기를 기다리지 않습니다. MySQL InnoDB와 PostgreSQL 모두 읽기에 MVCC를 씁니다. 쓰기끼리는 여전히 락으로 막습니다.

      격리 수준: 얼마나 엄격하게 막을까

      완전히 막을수록(직렬화) 대기·재시도가 늘어 느려집니다. 그래서 SQL 표준은 네 단계를 두고, 단계마다 허용하는 이상 현상이 다릅니다. 아래에서 직접 바꿔 보세요.

      직접 해 보기 · 두 트랜잭션 타임라인
      현상

      시간T1 (나)T2 (다른 사람)

      실제 DBMS는 표준과 조금 다릅니다. 기본 격리 수준은 MySQL InnoDB가 REPEATABLE READ, PostgreSQL이 READ COMMITTED입니다. InnoDB의 REPEATABLE READ는 일반 SELECT가 스냅샷을 읽어서 팬텀이 대부분 보이지 않습니다. PostgreSQL은 READ UNCOMMITTED를 받아도 READ COMMITTED처럼 동작해서 dirty read가 없습니다. 위 표는 시험용 표준 기준입니다.

      Lost update도 알아 두세요. T1과 T2가 둘 다 잔액 100,000을 읽고 각자 10,000을 빼서 90,000을 쓰면, 두 번 출금했는데 잔액은 90,000입니다. 쓰기 락(X)이나 SELECT … FOR UPDATE로 막습니다. S0의 6단계가 이 일을 합니다.

      확인 질문 1: READ COMMITTED에서 같은 SELECT를 두 번 했는데 값이 다르게 나왔다. 무슨 현상이고, 어떤 수준으로 올려야 막히나?
      Non-repeatable Read. 사이에 다른 트랜잭션이 그 행을 고치고 커밋했기 때문입니다. REPEATABLE READ 이상이면 막힙니다(트랜잭션 시작 시점 스냅샷을 계속 읽거나, 읽은 행에 락을 유지).
      확인 질문 2: Non-repeatable Read와 Phantom Read의 차이는?
      Non-repeatable은 이미 읽은 행의 값이 바뀐 것(UPDATE), Phantom은 조건에 맞는 행의 개수가 바뀐 것(INSERT/DELETE)입니다. 행 하나에 락을 거는 것만으로는 아직 없는 새 행을 막을 수 없어서 팬텀이 더 막기 어렵습니다.

      S6. 장애 복구: WAL, redo/undo, 체크포인트

      ★★10분

      WAL(Write-Ahead Logging) 규칙은 두 줄입니다.

      1. 데이터 페이지를 디스크에 쓰기 전에, 그 변경의 로그가 먼저 디스크에 있어야 한다.
      2. COMMIT 응답 전에, 그 트랜잭션의 로그가 전부 디스크에 있어야 한다.

      왜 로그를 먼저 쓰면 빠른가? 데이터 페이지는 디스크 여기저기 흩어져 있어서(랜덤 쓰기) 느리고, 로그는 파일 끝에 이어 붙이기만 해서(순차 쓰기) 빠릅니다. 그래서 커밋 때는 로그만 확실히 쓰고, 페이지는 나중에 모아서 씁니다.

      재시작 때 본 상황하는 일필요한 로그 내용
      로그에 COMMIT이 있는데, 데이터 페이지엔 반영 안 됨redo: 로그대로 다시 적용새 값
      로그에 COMMIT이 없는데, 데이터 페이지엔 이미 써짐undo: 이전 값으로 되돌림이전 값

      체크포인트. "여기까지의 dirty 페이지는 디스크에 다 썼다"는 표시입니다. 재시작 때 로그를 처음부터가 아니라 마지막 체크포인트부터 읽으면 됩니다. 안 하면? 로그가 몇 달 치 쌓였을 때 복구에 몇 시간이 걸립니다.

      미니 Redis에서 이미 만든 것

      미니 RedisDBMS공통 핵심
      AOF, 응답 전에 writeWAL데이터보다 로그를 먼저
      배치 write 1번group commit여러 커밋을 시스템 콜 한 번으로
      재시작 시 AOF 재실행redo 복구로그를 다시 적용해 상태를 만든다
      AOF 압축 (base + incr)체크포인트로그가 끝없이 커지지 않게
      멱등 레코드멱등 redo두 번 적용해도 결과가 같아야
      (없음)undo미니 Redis는 성공한 명령만 기록해서 되돌릴 일이 없었다
      확인 질문: 커밋 안 된 트랜잭션의 dirty 페이지를 디스크에 미리 써도 될까? 된다면 어떤 로그가 꼭 필요한가?
      됩니다(버퍼 풀 자리가 모자랄 때 실제로 그렇게 합니다). 대신 나중에 그 트랜잭션이 실패하면 되돌려야 하므로 undo 정보(이전 값)가 그 페이지보다 먼저 디스크에 있어야 합니다. WAL 규칙 1번이 바로 이것입니다.

      S7. 정규화·ER (훑기)

      ★5분

      정규화는 중복을 없애려고 테이블을 쪼개는 일입니다. 중복이 있으면 고칠 때 한 곳만 바뀌어 데이터가 어긋납니다(이상 현상: 삽입·수정·삭제 이상).

      정규형조건 (한 줄)어기는 예
      1NF칸 하나에 값 하나 (원자값)phone 칸에 "010-1, 010-2"
      2NF1NF + 기본키 일부에만 의존하는 열이 없음(학번, 과목) PK인데 학생 이름이 학번에만 의존
      3NF2NF + 키가 아닌 열을 거쳐 의존하는 열이 없음 (이행 의존)학번 → 학과 → 학과장
      BCNF모든 결정자가 후보키3NF지만 키가 아닌 열이 키 일부를 결정

      반정규화. 너무 쪼개면 조회 때 조인이 많아져 느립니다. 그래서 읽기가 압도적으로 많은 곳은 일부러 중복을 허용하기도 합니다(캐시를 두는 것과 같은 거래).

      ER 모델은 테이블을 만들기 전 설계 그림입니다. 개체(사각형: 학생, 과목), 속성(타원: 이름), 관계(마름모: 수강)와 관계의 수(1:1, 1:N, M:N)를 그립니다. M:N은 테이블로 바로 못 만들어서 중간 테이블(수강: 학번 FK, 과목코드 FK)을 둡니다.

      확인 질문: 학생과 과목은 M:N이다. 테이블로 옮기면 테이블이 몇 개 필요한가?
      3개입니다. 학생, 과목, 그리고 둘을 잇는 수강(학번, 과목코드를 FK로, 둘을 합쳐 PK로).

      예상 질문

      5분
      DB와 DBMS는 어떻게 다른가요?
      DB는 데이터 모음, DBMS는 그걸 관리하는 소프트웨어입니다. DBMS가 동시성 제어, 장애 복구, 질의 처리, 권한을 맡아서 앱이 파일을 직접 다룰 때 생기는 문제를 없앱니다.
      인덱스를 모든 열에 걸면 안 되는 이유는?
      쓰기마다 모든 인덱스를 같이 고쳐야 해서 INSERT/UPDATE가 느려지고, 공간도 듭니다. 자주 조회 조건(WHERE, JOIN, ORDER BY)에 쓰이고 값이 다양한 열에 겁니다.
      B+트리가 이진 탐색 트리보다 DB에 맞는 이유는?
      노드 하나가 페이지 하나라서 자식이 수백 개입니다. 트리가 낮아(높이 3~4) 디스크 읽기가 몇 번이면 끝납니다. 이진 트리는 높이가 log₂n이라 1억 행이면 27번 가까이 디스크를 읽습니다. 또 리프가 이어져 있어 범위 검색이 쉽습니다.
      ACID를 각각 무엇이 보장하나요?
      A: undo 로그. C: 제약 조건과 앱 로직. I: 락·MVCC. D: 커밋 전 로그 fsync와 redo.
      격리 수준을 항상 SERIALIZABLE로 하면 안 되나요?
      안전하지만 대기·교착 상태·재시도가 늘어 처리량이 떨어집니다. 그래서 기본값은 보통 READ COMMITTED나 REPEATABLE READ이고, 꼭 필요한 트랜잭션만 높입니다.
      MVCC가 뭐고 왜 쓰나요?
      행의 여러 버전을 남겨 두고, 읽는 트랜잭션은 자기 시점의 버전을 읽게 하는 방식입니다. 읽기와 쓰기가 서로 기다리지 않아 동시성이 높아집니다.
      커밋했는데 데이터 파일엔 아직 안 써졌습니다. 이때 장애가 나면?
      로그에 COMMIT이 있으므로 재시작 때 redo로 다시 적용합니다. 그래서 커밋된 내용은 사라지지 않습니다.
      WAL이 데이터를 바로 쓰는 것보다 빠른 이유는?
      로그는 파일 끝에 순차로 이어 쓰고 크기가 작습니다. 데이터 페이지는 흩어져 있어 랜덤 쓰기입니다. 커밋 때는 로그만 쓰고 페이지는 나중에 모아 쓰므로 빠릅니다.
      정규화를 왜 하고, 반정규화는 언제 하나요?
      중복을 없애 삽입·수정·삭제 이상을 막으려고 합니다. 조인이 너무 많아 읽기가 느려지는 곳에서는 일부러 중복을 두는 반정규화를 합니다.
