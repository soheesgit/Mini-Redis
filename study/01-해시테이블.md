# 01. 해시 테이블 ★★★ (1.5시간)

**한 줄 답**: 체이닝 해시 테이블입니다. 크기를 바꿀 때 한 번에 다 옮기지 않고 **명령 하나마다 버킷 1개씩** 옮겨서 서버가 멈추지 않게 합니다.

> 흐름: 명령 실행(Store) → **[키로 엔트리 찾기·넣기]** → 결과

## 꼭 알 것 3가지

**1. 버킷 번호 = `hash & (크기 - 1)`**
버킷 수는 항상 2의 거듭제곱입니다. 그래서 나머지 연산(`%`) 대신 AND 한 번으로 버킷 번호를 구합니다.

**2. 점진적 리해싱: 테이블이 잠깐 2개가 된다**

```
table[0] (옛, 4칸)        table[1] (새, 8칸)
 0 │ ∅  ← 옮김 끝          0 │ k1
 1 │ ∅  ← 옮김 끝          1 │
 2 │ k2 → k6   ← rehashIndex = 2 (다음에 옮길 곳)
 3 │ k3                    5 │ k5   ← 리해싱 중 새로 넣은 키
```

| 리해싱 중 동작 | 규칙 | 안 지키면 무엇이 깨지나 |
|---|---|---|
| 조회·삭제 | 두 테이블 모두 찾는다 | 옮겨진 키를 못 찾는다 |
| 새 키 추가 | **table[1]에만** 넣는다 | 이미 비운 버킷에 넣으면 영영 안 옮겨지고, 완료 때 table[0]과 함께 버려진다 |
| 진행 | 명령 1개마다 `rehashStep()` 1번 + 10ms마다 1ms | 한 번에 다 옮기면 키 100만 개일 때 수백 ms 멈춘다 |
| 빈 버킷 | 최대 10개까지만 건너뛴다 | 빈 버킷이 길게 이어지면 한 단계가 오래 걸린다 |

**3. 커서가 열려 있으면 리해싱과 크기 조정을 멈춘다**
커서는 엔트리 참조 대신 (테이블 번호, 버킷 번호)만 기억합니다. 버킷 배열이 바뀌지 않아야 이 번호가 계속 같은 곳을 가리킵니다.

## 예상 질문과 답

**Q. 왜 버킷 수를 2의 거듭제곱으로 하나요?**
`&` 한 번으로 버킷 번호를 구할 수 있습니다. 또 2배로 늘리면 해시에서 비트를 하나 더 보는 것이라, 버킷 i의 키는 새 테이블의 i 아니면 i+옛크기 둘 중 하나로만 갑니다.

**Q. 확장은 적재율 1인데 축소는 왜 1/8인가요? 1/2로 하면 안 되나요?**
경계가 가까우면 키를 넣고 빼는 것만 반복해도 확장과 축소가 번갈아 일어납니다(thrashing). 둘 사이를 넓게 벌려 둔 것입니다.

**Q. 리해싱 중에 커서가 계속 돌면 무엇이 깨지나요?**
이미 지나간 버킷의 키가 아직 안 본 위치로 옮겨지면 두 번 방문합니다(중복). 반대로 아직 안 본 키가 이미 지나간 위치로 옮겨지면 한 번도 방문하지 못합니다(누락). 참고로 Redis도 안전 반복자(safe iterator)에서는 리해싱을 멈춥니다. `SCAN`은 역비트 순서 커서라는 다른 방법을 씁니다.

**Q. 커서 때문에 리해싱이 멈추면 손해는 없나요?**
확장도 같이 멈추므로 체인이 길어집니다. 그래서 커서를 닫는 즉시 크기 조정을 판단하고, `/admin/stats`의 `maxChain`으로 체인 길이를 지켜봅니다.

**Q. 왜 SipHash를 쓰나요? Java `hashCode()`를 쓰면 안 되나요?**
`hashCode()`는 공식이 공개되어 있습니다. 그래서 공격자가 같은 버킷에 몰리는 키를 대량으로 만들 수 있고, 그러면 조회가 O(n)이 됩니다. SipHash는 무작위 시드를 모르면 그런 키를 만들 수 없습니다.

**Q. 기획서와 다른 점이 있나요?**
기획서는 엔트리 안에 `next`(체인)를 둡니다. 하지만 같은 엔트리가 키 테이블과 만료 테이블 두 곳에 들어가야 해서, 체인 노드(`Node`)를 테이블 안에 따로 두었습니다.

## 건너뛰어도 되는 것
SipHash의 라운드 연산(`round()`)은 건너뛰어도 됩니다. 테스트 벡터 4개가 맞는다는 것만 알면 됩니다. `randomEntry`의 범위 계산도 마찬가지입니다.
