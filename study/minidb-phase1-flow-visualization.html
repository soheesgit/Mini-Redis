미니 DBMS · Phase 1

SQL 한 줄이 파일의 바이트가 되기까지

글자로 된 SQL 한 줄이 렉서, 파서, 값 검사, 행 인코딩, 페이지를 거쳐 파일의 바이트가 되고, 다시 읽혀 나오는 과정을 한 단계씩 따라간다. 목표는 60분 안에 이 흐름을 머릿속에 그릴 수 있게 되는 것이다.

슬롯 · 키워드행 바이트지금 바뀐 것삭제 · 죽은 공간

따라갈 예시 입력

CREATE TABLE users (name VARCHAR(20), age INT);   -- id INT 칸은 맨 앞에 자동으로 붙는다INSERT INTO users VALUES ('kim', 20);             -- id는 적지 않는다. nextId가 정한다SELECT * FROM users WHERE age >= 20;UPDATE users SET name = 'kimchi' WHERE id = 1;DELETE FROM users WHERE id = 1;
아래 Java 코드는 학습용 축소판이다. INT · VARCHAR만 다루고, checksum은 자리만 있다. 렉서는 #22에 실제 코드(minidb/sql/Lexer.java)가 있고 나머지는 구현 전이다. 실제 코드는 이 페이지와 다를 수 있다.

왜 필요할까

SQL은 사람이 읽는 글자다. 파일에 들어가는 것은 바이트다. 글자를 그대로 파일에 적으면 "id가 1인 행"을 찾을 때마다 모든 글자를 다시 해석해야 하고, 행 하나를 고치면 뒤 내용이 전부 밀린다. 그래서 글자를 뜻이 정해진 바이트로 바꾸고, 8KB짜리 페이지 안의 정해진 자리에 넣는다.

등장하는 것들

토큰 일렬

렉서가 자른 단어 하나. 종류(KEYWORD, IDENT, NUMBER, STRING, 기호)와 글자를 가진다. 토큰 목록은 한 줄로 늘어선 배열이다. 누가 테이블 이름이고 누가 값인지는 아직 모른다.

AST 트리

추상 구문 트리. 문장의 뜻을 부모-자식 구조로 담는다. 괄호 · 쉼표 · 세미콜론은 구조를 알려 주는 역할을 끝냈으므로 AST에는 없다.

스키마

테이블의 칸 이름과 타입 목록. 여기서는 id INT, name VARCHAR(20), age INT. 테이블 파일의 0번 메타 페이지에 저장된다. 행 바이트에는 칸 이름이 없어서, 스키마 없이는 읽을 수 없다.

행 바이트 14B

행 하나를 바이트로 바꾼 것. [NULL 비트맵][칸0][칸1][칸2] 순서다. 숫자는 빅엔디언(큰 자리 바이트가 앞)으로 쓴다.

데이터 페이지 8192B

헤더 16바이트(0~15), 그 뒤로 슬롯이 앞에서 뒤로, 행이 맨 뒤에서 앞으로 채워진다. free_start는 다음 슬롯 자리, free_end는 마지막에 쓴 행의 시작이다.

nextId

다음 행에 줄 id. 실행기가 메모리에 들고 있다. 파일 쓰기가 성공한 뒤에만 1 올린다.

헷갈리는 점 · 예상 질문

    

      
왜 슬롯은 앞, 행은 뒤에서 채울까?

        
슬롯표와 행이 각각 얼마나 커질지 미리 알 수 없기 때문이다. 양 끝에서 마주 보며 채우면 가운데 빈 공간을 경계 없이 다 쓴다. 둘 다 앞에서 채우면 슬롯 자리를 미리 정해야 해서, 남거나 모자란다.

      
삭제할 때 왜 슬롯을 빼지 않을까?

        
슬롯을 빼면 뒤 슬롯의 번호가 하나씩 당겨진다. Phase 2의 인덱스는 행 위치를 (페이지, 슬롯 번호)로 기억하므로, 번호가 바뀌면 인덱스가 엉뚱한 행을 가리킨다. 그래서 offset = 0으로 표시만 한다.

      
렉서와 파서를 왜 나눌까?

        
하는 일과 잡는 에러가 다르다. 렉서는 글자 수준(닫히지 않은 따옴표, 모르는 글자), 파서는 순서 수준(FROM 누락, ; 누락)을 본다. 나누면 파서는 공백 · 대소문자 · 따옴표를 신경 쓰지 않고 토큰 종류만 대조하면 된다.

      
nextId를 왜 쓰기 성공 뒤에 올릴까?

        
쓰기가 실패했는데 nextId가 이미 올라가 있으면, 파일에 없는 행이 그 id를 차지한 셈이 된다. "성공한 것만 반영한다"는 순서를 지키려고 맨 마지막에 올린다. 인덱스 등록(Phase 2)도 같은 이유로 파일에 쓴 뒤에 한다.

      
UPDATE로 행이 길어지면?

        
세 경우로 나뉜다 (설계 1.9).

        

          
조건하는 일슬롯

          
새 길이 ≤ 예전 길이제자리에 덮어쓴다length만 바뀜

          
같은 페이지 빈 공간 ≥ 새 길이free_end 쪽에 새로 쓴다. 예전 바이트는 죽은 공간번호 유지, offset만 바뀜

          
둘 다 아님다른 페이지로 옮긴다 [확정]. 예전 슬롯은 삭제 표시, 같은 id로 마지막 페이지에 삽입(페이지, 슬롯)이 바뀜 → Phase 2에서 인덱스 갱신

        

    

    

      nextId의 한계 [확정] — 실행 중에는 지운 id를 다시 쓰지 않는다(nextId는 줄지 않는다). 하지만 nextId는 파일에 저장하지 않고, 시작할 때 모든 데이터 페이지를 훑어 "최대 id + 1"로 복원한다. 그래서 마지막 id의 행을 지우고 재시작하면 그 id가 다시 쓰인다. 설계 1.7에 한계로 적혀 있다.
    

    

      죽은 공간 처리 [확정] — 삭제된 슬롯은 재사용하지 않는다. 당겨 모음(compaction)은 UPDATE에서 "빈 공간 합은 충분한데 연속 공간이 모자랄 때"만 한다 (설계 1.10).
    

  


  

    
핵심 정리

    
    
      
  • SQL 문자열 → 렉서(토큰 목록) → 파서(AST) → 값 검사 → 행 인코딩(바이트) → 페이지 · 슬롯 → 파일. 단계마다 잡는 에러가 다르다.
    • 
      
  • 페이지는 슬롯을 앞에서, 행을 뒤에서 채운다. 삭제와 길어지는 UPDATE는 슬롯 번호를 그대로 두고 offset만 바꾼다. 남은 바이트는 죽은 공간이 된다.
    • 
      
  • SELECT는 거꾸로다. 페이지를 훑고, 슬롯을 따라가 바이트를 읽고, 스키마 순서대로 디코딩한 뒤 WHERE가 참인 행만 내보낸다.
    • 
    

    
확인 질문

    
1. 'kim' 행을 넣은 직후(UPDATE 전)에 INSERT INTO users VALUES ('park', 25);를 실행한다. 새 행의 16진수 바이트, 길이, 행 위치, 슬롯 1의 값과 위치, free_start, free_end, 남은 공간을 모두 적어라.
      
바이트: 00 | 00 00 00 02 | 00 04 70 61 72 6B | 00 00 00 19 (id = 2, 길이 4, 'p' 'a' 'r' 'k', 25 = 0x19)

      
길이: 1 + 4 + (2 + 4) + 4 = 15바이트

      
행 위치: 8178 − 15 = 8163 (8163~8177). 슬롯 1: (8163, 15), 위치 20~23

      
free_start: 20 → 24. free_end: 8178 → 8163. 남은 공간: 8163 − 24 = 8139

      
채점: 하나라도 틀리면 부분 정답. id를 1로 적었거나 행 위치를 8192에서 뺐으면 오답.

    
2. DELETE가 슬롯 0을 슬롯표에서 아예 빼고 뒤 슬롯을 당긴다면 무엇이 깨지는가? 그리고 offset = 0이 "삭제됨" 표시로 쓰여도 진짜 행과 헷갈리지 않는 이유는?
      
깨지는 것: 뒤 슬롯의 번호가 하나씩 바뀐다. 인덱스가 기억한 (페이지, 슬롯)이 다른 행을 가리키게 된다.

      
헷갈리지 않는 이유: 페이지의 0~15바이트는 헤더다. 행은 그 자리에서 시작할 수 없으므로 offset 0은 진짜 행 위치로 나올 수 없는 값이다.

      
채점: 두 부분을 모두 맞혀야 정답. "인덱스가 깨진다"만 쓰고 왜(번호가 바뀜)를 안 썼으면 부분 정답.
