# 05. 메모리 상한과 LRU ★ (0.5시간)

**한 줄 답**: 엔트리마다 사용량을 추정해서 더해 둡니다. 쓰기 전에 상한을 넘었으면 **가장 오래 안 쓴 키**부터 지우고, 지울 수 없으면 507을 냅니다.

> 흐름: 쓰기 명령 도착 → **[상한 검사 → 필요하면 제거]** → 실행

## 꼭 알 것

**1. 사용량 = 키 바이트 + 값 바이트 + C (+ TTL 있으면 32)**
Java는 GC를 쓰기 때문에 실제 메모리를 정확히 잴 수 없어서 추정치를 씁니다. C는 엔트리 1개의 JVM 고정 비용입니다. 키 100만 개를 넣어 힙 증가분으로 쟀더니 **C ≈ 139바이트**였습니다(기획서 초깃값 112). 체인 노드와 버킷 배열 몫이 더해진 결과입니다.

**2. 정확한 LRU = 이중 연결 리스트**

```
앞(최근) ⇄ e ⇄ ... ⇄ 뒤(가장 오래됨) ← 여기서 제거
```

키를 읽거나 쓸 때마다 맨 앞으로 옮깁니다. 리스트는 2개입니다. 전체 키 리스트(`allkeys-lru`용)와 TTL 키만 모은 리스트(`volatile-lru`용)입니다. 엔트리 안에 prev/next를 두기 때문에 이동과 삭제가 모두 O(1)입니다.

| 정책 | 지우는 대상 |
|---|---|
| `noeviction` (기본) | 지우지 않고 쓰기를 거부 (507) |
| `allkeys-lru` | 전체 리스트의 맨 뒤 |
| `volatile-lru` | TTL 리스트의 맨 뒤. TTL 키가 없으면 507 |

**3. LRU로 지운 키도 AOF에 `DEL`로 남긴다** (03의 멱등 레코드와 같은 이유)

## 예상 질문과 답

**Q. 실제 Redis도 정확한 LRU인가요?**
아닙니다. Redis는 키 몇 개를 무작위로 뽑아 그중 가장 오래된 것을 지우는 근사 LRU입니다. 엔트리마다 포인터를 두지 않아 메모리를 아끼는 대신 순서가 결정적이지 않습니다. 이 프로젝트는 테스트로 제거 순서를 증명하려고 정확한 LRU를 골랐습니다. 대가는 엔트리마다 포인터 4개입니다.

**Q. `LinkedHashMap`의 접근 순서 기능을 쓰면 되지 않나요?**
직접 만든 해시 테이블과 엔트리를 공유해야 해서 쓸 수 없습니다.

**Q. DEL도 메모리 상한에 막히나요?**
아닙니다. 메모리를 줄이는 명령이므로 막지 않습니다. 상한 검사는 SET과 INCR에만 합니다.
